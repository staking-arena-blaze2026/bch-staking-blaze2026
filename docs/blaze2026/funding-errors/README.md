# Reward validation and verified funding diagnostics

Post-baseline hackathon work. No category, authenticated list, covenant bytecode or wallet approval design changed. Public RPC inspection was read-only; all signing and relay tests used fresh isolated BCHN data directories and synthetic keys.

## Precise cause of the observed mainnet failure

The live preflight reported **867,701 verified satoshis**, of which **866,201 were excluded by legacy operation `f7bebfca-afb1-4ed3-a784-2ae8bdf3b019`**. Only **1,500 satoshis** and **zero eligible genesis inputs** remained unreserved. The tested first preparation needed **1,765 satoshis**, including 219 fee satoshis, a 1,000-satoshi output and 546-satoshi non-dust change. Its later creation fee had not yet been quoted. The wallet owner reached no signing prompt. See [live report and public verification](live-reservation-evidence.json).

This identifies the failure as a **legacy signed-input/continuation reservation**, rather than missing wallet derivations, a low total BCH balance or an incorrectly sized fee for the complete available wallet. Automatic preparation cannot use inputs protected by an unresolved signed transaction. A distinct, adequately funded unreserved input set can create another vault without consuming the legacy reservation.

The initially supplied transaction ID `f78da01290029f135ddd7a37df125ba5843327363970905d484c9e31790b0c67` is the **funding parent**, confirmed in block 977833. The recovery row subsequently identified the actual signed `seed-funding` child as **`fcfe15444eea8a0fd0c941e40de17769d4acc28d2206840235c1885fed9174c2`**. The initial interpretation that the child journal itself was stale was incorrect: parent and child are different transactions.

Both configured mainnet providers (`bch.loping.net`, `bch.imaginary.cash`) independently agreed on tip 977884 and returned “No such mempool or blockchain transaction” for the child at inspection. They also independently verified that both parent outputs were still unspent: output zero holds 1,200 satoshis and output one holds 865,001. Together these equal the **866,201-satoshi reservation**. The third wallet output, `0365de35ea47894bafc6515d1d4eca48d67c1d645a3ce54496c51a8e42606243:3`, holds the remaining 1,500. All are token-free P2PKH outputs. The parent's original 866,420-satoshi input is spent; confirmation of that spend does not settle a signed child referencing the parent's outputs.

A missing transaction response is **not proof that the retained child signatures can never spend those inputs later**. Consequently this reservation cannot safely be released automatically from parent confirmation or absence in those providers' histories. Signed bytes remain retained. Inspect / resume is read-only for this legacy entry; it does not retry, broadcast, advance or abandon it. The new [explicit resolution flow](recovery.md) can replace a verified wallet-only legacy spend with a user-approved self-send. Reservations release only after independent confirmation of that competing spend. Covenant/unknown funds retain the manual inspection path. Separate verified unreserved funding remains usable for unrelated creation. Covenant-controlled funds are never automatically consumed or abandoned.

The complete public wallet layout has one eligible output-zero origin. With its inputs available, the original, unmodified source planner and the repaired planner both quote an ordinary self-send followed by atomic creation: **two transactions and two approvals**. At the observed 1 sat/byte policy the measured size projection is 185 + 732 = **917 fee satoshis**. Reserve 9,600 + covenant carriers 2,400 + discovery listing 1,000 + fees 917 = **13,917 satoshis committed**, with wallet change retained. This is conditional on those inputs being legitimately available; it is not the current spendable quote while the reservation is unresolved. See the [unmodified planner projection](original-planner-projection.json), [initial public observations](public-mainnet-evidence.json) and [isolated signed/P2P results](reported-layout-regtest.json). No public transaction was signed or broadcast during these checks.

## Repairs

Creation and offer constraints now share protocol validation and field-specific messages. The BCH minimum is permanently beside the reward label, with immediate correction feedback. CashTokens use exact raw fungible units (minimum one for rewards); token decimals are never inferred. Disabled form actions explain field, wallet, busy and verification reasons. Preflight failures remain next to the action until success or dismissal, retain form values and survive progress/list refreshes. Worker failures preserve structured evidence and display a single message without repeated `Error:` prefixes.

Funding failures retain verified/unreserved/reserved totals, supplied descriptor count, eligible genesis count, relevant reservation IDs, measured candidate requirements and fees when available, and the preparation result. An incomplete preparation quote is explicitly distinguished from a complete sequence quote; unknown fee totals are not invented. The sufficient candidate requirement includes a non-dust wallet-change output and is not presented as a universal theoretical minimum. BCH on NFTs is never selected. The 16-input bound and heavily fragmented funding corrective path remain explicit.

A reproduced planning bug affected BCH attached to unrelated **fungible** token categories: the direct planner excluded these inputs even when their BCH could fund creation. A fully quoted wallet-only consolidation fallback preserves every fungible token category, prepares independent origins and then uses the existing atomic transaction. NFTs and covenant outputs are never consolidation candidates. A direct funded atomic plan still takes priority. Sufficient BCH fragmented beyond the atomic 16-input bound also uses bounded consolidation, instead of reporting a false overall balance shortage.

Every relevant signed journal is reconciled against independently verified transaction bytes/status or a confirmed competing input spend before reservations are released. Its actual signed input outpoints must match the journal sources; a confirmed parent cannot clear a different child’s reservations. If transaction status remains unavailable but its inputs can be independently verified as unspent, the inspector reports their exact count, BCH amount and verified tip while keeping the reservation. Signed bytes and historical fields remain intact. An inconclusive status keeps its unspent inputs reserved and explains how to inspect them. A confirmed ordinary legacy self-send no longer leaves a stale signed classification. Legacy covenant/NFT/non-wallet outputs keep continuation reservations; explicitly named `queueCoin`/`seed` anchors remain protected while their status/scripts are unknown or a non-wallet seed is referenced. Independently confirmed ordinary wallet self-sends with exclusively P2PKH references release obsolete continuation reservations, preserving all historical fields. Legacy Inspect / resume never signs, rebroadcasts or advances a legacy covenant. The UI does not offer Retry identical transaction for legacy entries. Ordinary preparation continuation reservations also survive parent confirmation until the child is recorded. A further reservation gap was fixed: original spent inputs alone did not reserve a self-send’s new outputs. The exact outputs derived from validated signed bytes are now durably reserved on retain and reconstructed for existing signed preparation journals. An unrelated new request cannot take the approved sequence’s continuation outputs; the related child can use them after independent verification. When previously spent inputs reappear after a reorganization, cached confirmed/conflict classifications are rechecked against the current chain; inconclusive signed transactions regain reservations. Both network configurations test this with block invalidation and a restart without mempool.
