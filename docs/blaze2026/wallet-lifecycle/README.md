# Wallet intent lifecycle and progressive creation discovery

Post-baseline BCH Blaze work, November 18, 2026. No contract artifacts, category rules, queue ordering or asset accounting are changed.

## Root causes and lifecycle

`restoreWalletRequest()` returned a guard that kept enforcing both wall-clock and monotonic 90-second restoration deadlines. The browser called that guard after discovery, preparation and the additional-approvals dialog. Even perfectly unchanged consent could therefore fail before Cashonize was asked to sign. The rejected guard could also strand the unsigned plan’s funding reservation, making later retries appear unfunded. Cancellation before a signing prompt now discards only a provably unsigned plan; the worker refuses discarding signed bytes or uncertain signing requests. A stranded unsigned request from an earlier attempt can be explicitly cancelled from the funding error panel without signing or deleting its journal. Separately, the financial worker had a cumulative 90-second RPC timeout that could terminate ongoing verification. Preparation also jumped from two indices per path to all forty, rescanning previously checked children and rechecking unrelated legacy signed requests.

Restoration now has its own bounded wait and distinct connection-timeout error. After a live wallet is restored, the intent guard checks cancellation, live availability, pairing generation, identity, network and form/navigation state without an elapsed-time deadline. Form edits have an epoch as well as a fingerprint: changing a value and changing it back does not restore obsolete consent. Page interruption invalidates pending intent, including a page restored from the back/forward cache. The preparation popup has no timer.

The worker sends liveness and stage messages while independent provider operations run. Its 90-second watchdog now detects an unresponsive worker rather than limiting cumulative verification duration. Electrum transport requests retain their individual timeouts and verification retries remain bounded. The dialog does not hold an outstanding financial worker request.

Every signing step independently refreshes its exact inputs, ancestry, chain context and relay-fee policy **after** confirmation. Both wall-clock and monotonic authorization age must remain within ten seconds at `beginSigning`, including after its durable journal write. The browser checks freshness again immediately before the Cashonize call. Authorization is never recovered from a durable journal. A proven ordinary extension can reauthorize the identical reviewed body with fresh independent input proofs and finality checks; reorganizations and changed fees trigger preparation again, with renewed consent for changed costs. Unavailable or conflicting providers never authorize.

Returned signed bytes are retained before any post-signing session guard. A sequence-bound authenticated response listener also journals bytes delivered after the SDK has cancelled and rejected its signing promise; it never broadcasts, re-signs, or accepts another request’s response. Network departure blocks new signing and broadcast while allowing the original, network-bound financial worker to journal a late response. Browser termination cannot guarantee delivery of a wallet response that has not reached the browser; requested/uncertain journal entries keep their reservations for recovery. There is no automatic legacy broadcast, erasure of evidence, or release based on a missing transaction response.

## Documented discovery boundary

- Start with indices 0 and 1 on each supported receive/change/defi path, adding previously used signing children from journals belonging to the same authenticated owner. Journal hints are checked against the live session's public derivation, and only needed public keys are derived.
- Expand by at most eight indices per path: 2, 8, 16, 24, 32, 40. A fully funded, independently checked one-transaction plan is already optimal and may stop immediately.
- A fallback popup is only offered after **all forty indices on every supported path plus authenticated historical signing hints** have been checked. This is a bounded policy, not a claim to discover arbitrarily deep HD-wallet children. Indices up to 199 from authenticated journal hints remain supported.
- Address candidates are scoped to one discovery ID, provider and exact tip. Expansion requests only new address candidates. Failed reads or verification clear the affected candidates. A new discovery or tip starts fresh. Candidate UTXOs are never spendability proof: funded scripts are independently re-read and their outputs/ancestry verified, and selected inputs are freshly verified again before each signature and broadcast.
- Each provider performs at most four concurrent address reads, draining every batch before transport teardown. The public providers use separate ElectrumCore readers; adapters without independent-reader support remain serial across providers. Legacy inventory scanning also runs providers independently and coalesces transaction proofs shared by multiple outputs within a scan. No provider-specific transaction history, unspent list or authorization is imported from another network/provider.
- Equivalent preliminary creation sequences can be reused within the same discovery only when parameters, complete candidate coins, owner, rate and exact tip are identical. The fee solver still uses actual serialized transaction sizes. Preparation continuation narrows inventory to the already reserved sequence's funding scripts and self-send destination.

## Historical reservations

Only operations intersecting current funding outpoints, retained continuation anchors, or the signed transaction's own live outputs are reconciled during new creation. Unrelated entries retain every existing reservation and signed byte. An unresolved reservation with independently verified unspent-input evidence can skip historical status lookup at the same tip **only when every actual signed input is again independently verified and identical**. This shortcut retains the reservation; it cannot release one. Changed tips, changed/missing inputs, conflicts and explicit recovery require reconciliation. Existing independent confirmation, conflicting-spend and reorganization protections remain in force.

## Measurements and verification

Browser `arena-wallet-timing` events report restoration, public-key derivation, confirmation, signing authorization, time to first approval, signing, signed-byte validation and broadcast. Worker events report discovery, UTXO retrieval, input verification, independent-provider verification, relevant legacy reconciliation, preliminary planning, exact fee calculation, preparation continuation and operation timing. Counters include Electrum methods, addresses observed per provider, candidate requests/plan builds avoided and verification retries. Events contain stage labels, durations and counts, not wallet addresses, keys, outpoints, transaction bytes or relay credentials. Nested durations overlap and must not be added together.

The isolated benchmark compares the actual baseline wallet module at the recorded source revision with the optimized implementation, alternating seven runs per implementation in each application network configuration. Both use the same isolated BCHN chain, confirmed synthetic wallet funding and an injected five-millisecond address-read delay. The recorded baseline source is `a718a1d40c917a272aa815d764fa66ea82e2a914`. Initial-address funding uses two descriptors for **both** implementations; later-address funding reproduces the baseline 2→40 expansion versus progressive discovery to indices 22/23. Timings include planning and fresh authorization, ending before the physical wallet/UI prompt. The regtest adapter deliberately does not claim parallel independent transports: only the public transport implementation provides these. Public-network latency and user/Cashonize response time cannot be inferred from these local results. With seven samples, p95 is the slowest observed sample and remains a small-sample estimate.

`preparation-results.json` records twenty isolated mainnet/chipnet application scenarios, including all four normal/fallback layouts and every BCH/token combination, exact signed-byte fees, minimum approval counts, interrupted continuation and loopback P2P relay. `wallet-results.json` additionally covers one-approval offer insertion, cancellation, reward claims, maturity withdrawal, review/session changes, tip extension, reorganizations and retained signed bytes. Synthetic-wallet frontend regressions cover >90-second verification/popup review in both configurations, cancellation, reconnection, late signatures and complete progressive discovery boundaries. No real mainnet or public chipnet funds were broadcast, and no physical Cashonize test is claimed.

Older wallet-scan assertions expected raw provider exception text, serialized session counts and automatic retry after proven forks; these assertions were already failing against the baseline module. They now check sanitized quorum errors, discarded snapshots, bounded retries, separate concurrent sessions and retained conflict protection. No production verification rule was relaxed to satisfy them.

Remaining limits: fallback discovery must still complete the documented forty-index boundary; public provider round trips, ancestry depth and independent verification remain material costs. Immutable txid-checked bytes and exact-tip linked header windows were already cached and remain provider/network isolated; live histories and spendability are deliberately refreshed. Protocol-level Electrum JSON-RPC batch support is not assumed; bounded concurrent requests use the existing transport. Physical Cashonize/browser lifecycle acceptance still requires the wallet owner.

## Measured results

Seven alternating runs per implementation and case, ending at fresh authorization. Milliseconds rounded below; raw samples and method counts are in `discovery-performance.json`. These are isolated component/workflow measurements, not physical Cashonize or public Electrum measurements.

| Application configuration / funding | Median before → after | p95 before → after | Electrum requests before → after | Final scan boundary before → after |
| --- | ---: | ---: | ---: | ---: |
| mainnet / initial addresses | 5850 → 4973 | 10171 → 9729 | 136 → 136 | 2 → 2 |
| mainnet / indices 22/23 | 1650 → 948 | 6172 → 3023 | 262 → 238 | 40 → 24 |
| chipnet / initial addresses | 809 → 616 | 1175 → 953 | 148 → 148 | 2 → 2 |
| chipnet / indices 22/23 | 1293 → 957 | 2363 → 4526 | 274 → 250 | 40 → 24 |

Late-address median latency improved by 43% on mainnet and 26% on chipnet, with 24 fewer Electrum method calls in both cases. Initial-address medians improved by 15% and 24%; request counts are unchanged for this already-short path. Chipnet’s late-address p95 **regressed** from 2.36 to 4.53 seconds. This small-sample tail result and substantial host contention mean consistent tail-latency improvement is not established.

The first exploratory run used more frequent four-index expansion and unconfirmed funding. Its late-address medians regressed despite scanning fewer addresses (`discovery-exploratory.json`). This exposed the per-batch setup/verification overhead and led to the bounded eight-index policy. The final confirmed-funding comparison is a separate controlled benchmark; these two experiments must not be compared as if funding confirmation and host load were unchanged. Unconfirmed paths are covered by the separate BCHN/P2P integration tests, not a claim of measured public-network speed.

To reproduce the comparison, materialize only the baseline source module with `git show a718a1d40c917a272aa815d764fa66ea82e2a914:src/queue/wallet.ts > src/queue/.baseline-wallet.ts`, then run `ARENA_NETWORK=regtest QUEUE_BASELINE_MODULE=../src/queue/.baseline-wallet.ts QUEUE_DISCOVERY_RESULTS=/tmp/discovery-performance.json npx tsx --test tests/queue-discovery-performance.test.ts`. Delete that temporary module afterwards; it is not a compatibility layer or deployed artifact.
