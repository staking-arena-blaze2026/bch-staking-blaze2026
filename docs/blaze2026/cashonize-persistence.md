# Persistent Cashonize connection (BCH Blaze 2026)

This is post-baseline fork work. No staking contracts or transaction verification rules change.

The finite retry behavior described below is historical and superseded by [automatic restoration repair](cashonize-auto-restoration.md).

## Diagnosis

Inspected the installed `@wizardconnect/react` 0.2.3, dapp manager and core 0.2.5 source and public declarations. The existing `staking-arena-wizardconnect-v1` record already supports cross-visit pairing. The SDK `loadSession`, manager `attachRelay`, and `existingCredentials` shape preserve the transport identity and wallet public paths.

The original component's `[manager, active]` cleanup calls `destroy` when the manager changes, `active` changes, or the effect is torn down. Ordinary connected-to-reconnecting transitions keep `active=true`, so this cleanup **does not itself prove** the reported loop. `destroy` stops manager keepalive/grace timers; relay cleanup is a separate responsibility. The SDK hook also owns destruction, creating conflicting ownership. Its StrictMode restoration creates two manager/relay instances; its remote disconnect handler unconditionally deletes the session. `wizardSdkLifecycle.test.tsx` reproduces duplicate restoration and session deletion using the actual SDK hook and a simulated transport. The original `networkRevision` effect dependency additionally recreates the browser worker on network invalidation/acceptance, disrupting the transaction client and public discovery. This is a reproduced set of failure mechanisms, not a claim that a particular user's real Cashonize trace was captured.

The core convenience connection manager resets its single-flight loop variable on errors and leaves a paused loop sleeping after cleanup. The new adapter owns a bounded serialized connection loop using the public `RelayClient` and key-exchange/URI primitives instead. Its subscription is attached to the protocol manager before network connection starts. The SDK still handles the encrypted wire protocol, peer filtering, chunking, persistence, public derivation and explicit wallet signing.

## Ownership and restoration

`usePersistentWallet.ts` owns one manager/relay pair. React StrictMode cleanup is deferred to a microtask and cancelled by the immediate effect replay. Normal renders, status changes, and Create a Vault/Make an Offer navigation do not transfer ownership. Real unmount, replacement, explicit disconnect and invalidation remove listeners, close transport, and destroy the obsolete manager. Transaction worker cleanup aborts its outstanding approvals and retains IndexedDB journals. Per-manager storage guards reject late writes from obsolete SDK handshakes; a teardown listener also stops any keepalive started after a delayed handshake finishes. A regression test reproduces this asynchronous disconnect race and verifies that session storage and timers remain cleared.

Startup reads the same storage key. A saved wallet public key selects **restoration only**: the exact stored transport key, pairing secret and wallet peer are reused; no new pairing URI is exposed. Cached public paths never establish live wallet/network authorization. A live `walletready` handshake and the existing chipnet boundary are required. Saved derivation identity is pinned; changed paths block the connection and cannot overwrite the previously accepted identity. An invalid-session marker survives reload until explicit replacement/disconnect.

The SDK record necessarily includes a **transport private key and pairing secret**. These are encrypted-messaging credentials, not BCH wallet private keys, seed phrases, or spending consent. They are stored only through the SDK session mechanism with a storage adapter that catches browser storage failures. No additional wallet spending credentials or signing approvals are persisted. Logs contain fixed lifecycle labels only, never credential values, URIs, paths, signatures or transaction contents.

Handshake retries run at 2, 6 and 14 seconds, with a 30-second deadline. The transport has a separate serialized bounded backoff budget. Duplicate notifications do not extend the deadline or overlap attempts. At the deadline the UI shows connection lost/unavailable and offers saved Retry, explicit replacement, and disconnect. A reachable relay remains passively subscribed for a later wallet handshake without active handshake polling. Unreachable transport is closed; Retry, browser online/focus/visibility events can begin another bounded restoration. Temporary silence never clears a pairing. Protocol/identity rejection and corrupt credentials have a distinct pairing recovery path. Cashonize can also use `user_disconnect` for keepalive recovery, so that ambiguous signal retains the saved pairing and attempts a bounded handshake; it never implies revocation merely from silence. New pairing approval is also bounded (two minutes).

Browser workers no longer depend on display/network revision. The same manager retains its worker and derived-key cache through harmless handshake repeats and transport recovery. Manager replacement closes the old worker. An authorization revision invalidates asynchronous preparation across interruptions or network/identity changes, even if the same wallet reconnects before preparation completes. Existing pre-sign/post-sign chain checks, provider/input verification, derivation ownership, token safety, 0-conf checks and journal recovery remain in place. Reconnection never invokes signing.

## Verification and limits

Validation results are recorded in `cashonize-persistence-results.json`; the deployment release manifest identifies the source revision. The existing browser marketplace test had one obsolete assertion for header links removed by earlier fork work; it now verifies the current header wallet action instead. Browser persistence tests use the production App, React StrictMode, actual SDK manager, localStorage and IndexedDB, with a **synthetic wallet transport** substituted only by a dedicated test Vite configuration. The production build cannot select that fixture. Browser-process restart tests close Chromium and relaunch the same temporary on-disk profile. The simulated computer restart likewise discards browser/JavaScript processes while retaining profile state; it is **not an actual OS reboot** and is not a branded Chrome test.

The browser tests cover first pairing, refresh, tab close/reopen, repeated browser process starts, simulated restart, offline startup/deadline, saved retry, late availability, relay interruption, no automatic QR, navigation, explicit disconnect, remote invalidation, separate profiles, clearing pairing, and preservation of a synthetic pending record in the actual v1 transaction IndexedDB store. Unit tests additionally cover StrictMode ownership, cached-path signing rejection, changed identity, mainnet/network checks, storage denial, worker reuse, backoff cancellation, interrupted preparation and obsolete-worker rejection. Existing recovery/security regressions are also run. None of these synthetic-wallet tests establish real Cashonize behavior.

Platform limitations: the same origin and browser profile/storage must survive; incognito, profile changes, clearing/denying storage, and revoked sessions require pairing again. hdwalletv1 exposes no independent expiry/revocation query and does not attest the exact testnet chain. Silence stays classified as unavailable, not revoked; protocol rejection is treated as invalid; ambiguous remote user disconnect retains the pairing and exposes retry/replacement after the bounded window. Exact chipnet transaction inputs still require independent provider verification before explicit spending approval. Cashonize must keep or reopen its own matching wallet/session and its encrypted transport must be reachable. Browser background throttling, wallet session retention, relay availability and an actual OS restart require real platform verification.

A fresh isolated headless probe reached the real Cashonize site but remained at onboarding after attempting its new-wallet control. It did not establish a pairing or a real wallet handshake. That profile was discarded. Real Cashonize pairing/reconnection, branded Chrome restart, and an actual OS restart are **not verified** by this change. No existing wallet/profile was inspected, no spending was requested, and no chipnet transaction was made.

Run checks with `npm --prefix frontend test`, `npm --prefix frontend run test:wallet:browser`, `ARENA_BROWSER_PORT=5174 npm --prefix frontend run test:browser`, `npm --prefix frontend run test:v3:browser`, `npm run typecheck`, and `npm run blaze:build`. After publishing, `node frontend/scripts/verify-wallet-release.mjs SOURCE_SHA` checks the live release manifest, every asset hash, production pairing/cancellation, saved restoration without QR, bounded offline UI, signing-disabled state, disconnect and mobile layout. Its deployed saved-session probe is synthetic and blocks all WebSockets; it cannot verify a live wallet handshake.
