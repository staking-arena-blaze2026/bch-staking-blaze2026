# Immediate submitted-offer visibility (post-baseline BCH Blaze work)

## Diagnosis

At source baseline `491452a`, `V3Arena.transact` announced registration but only rendered offers decoded from the independently verified snapshot. A successful refresh could still return the previous vault state: acknowledgement from the broadcasting peer does not establish propagation to the other verification peers. A refresh error also left the old snapshot visible. The confirmed replay cache already rechecks relevant histories, live outputs and the tip; removing these checks or injecting local transactions into the replay would weaken authorization.

The former 20-second recovery loop separately replayed every signed operation before refreshing the selected queue. One failed inspection could prevent subsequent journal loads and queue refreshes. Atomic recovery mapped both provider failure and absence back to `prepared`, losing the display distinction between acknowledged submission and uncertain broadcast. The generic operation block advised reconciling or discarding even when signed evidence was retained.

## Implementation

- A separate `SubmittedOffers` table uses retained journal terms and signed bytes as display evidence. Accepted offers appear immediately when the wallet worker returns, without a provider request. It shows stake, duration, reward, full txid and **Unranked**. It never enters local terms into `rankings`, contract replay, balances or financial authorization.
- Durable `acceptedAt` records an exact matching broadcast acknowledgement. Missing acknowledgement remains uncertain, even if broadcasting may have succeeded. `observation` and `verifiedAt` record independent replay results separately. Old `pending` journals remain readable. Failed verification cannot erase signed bytes or acceptance history.
- Prepared unsigned, wallet refusal, uncertain signed, accepted/propagating, independently verified pending, confirmed, conflicted and no-longer-observed states have distinct text. Missing transactions after previous verification or a 120-second acceptance grace are labelled possibly rejected/evicted; absence is not asserted to prove which event occurred. Provider unavailability is not eviction evidence. Journal observations are explicitly not proof of current confirmation.
- A selected-vault sync returns journal inspection proposals derived from **the same independent snapshot** used to render its queue. The financial worker applies each only if the retained journal still equals the inspected original. Existing Web Locks and compare-before-write protections remain. A snapshot containing the submitted txid removes its separate unranked row and supplies the live ranking.
- Recovery uses serial completion-based delays of 1, 2, 4, 8, 15, 30 and then 60 seconds. There is one active pass, capped passive polling thereafter, and at most four rotating background inspections per pass. The selected vault is checked first. Provider failures retry; wallet disconnects and reloads do not require user action to resume verification. Confirmed/conflicted journals remain subject to reorg checks.
- Signed evidence is never offered for discard. Explicit identical-byte retries still run existing recovery, source, funding, ancestry, signature, chain and wallet checks. No automatic rebroadcast was added. Rejected or evicted transactions can require an explicit safe recovery decision; passive reconciliation does not silently spend new coins.
- `accepted-to-provisional-row` and `accepted-to-verified-queue` timing events are privacy-safe durations with no raw transactions, addresses or terms. Reload-derived timings include time since the original acknowledgement and must not be mistaken for warm render latency.

No covenant bytecode, blockchain security checks, wallet approval protocol or original deployment was changed. All integration node state is isolated in temporary regtest directories.

## Validation and measurement boundary

Unit/React coverage includes immediate unranked display over an old snapshot, failed refresh, slow verification, uncertain acknowledgement, rejection, propagation grace, asymmetric-provider failure, automatic promotion using a shared snapshot, journal consistency, confirmation, reorg, eviction, conflict, repeated journal recovery, disconnected wallets and absence of automatic rebroadcast.

The loopback WSS browser fixture constructs a valid Atomic V4 genesis and signed offer with compiled covenant validation. It retains the offer journal while both providers expose the preceding state, exposes the offer asymmetrically, reloads repeatedly without a connected wallet, then exposes it to both providers and mines a synthetic confirmation. These synthetic headers are not public blockchain confirmations. No real BCH is spent.

Before: there was **no provisional row**, so acceptance-to-provisional visibility had no finite value; only a later successful independent replay could make the offer visible. No live Cashonize approval or mainnet broadcast was performed for this change, so no before/after mainnet latency is claimed. Measured synthetic warm-render, cold-reload and propagation-to-ranking results are reported separately in the validation evidence.

Recorded run: the synthetic warm click-to-provisional-row upper bound was **193 ms**. Cold browser navigation/reload with a retained accepted journal took **2,995 ms** to show the provisional row. With deliberate old-state exposure, asymmetric propagation and repeated reloads, independently verified ranking appeared **12,566 ms** after the injected acknowledgement timestamp, or **1,499 ms** after both providers exposed the offer. Baseline `491452a` had no separate provisional row, so there is no comparable finite baseline provisional-render time. These are fixture measurements, not real-wallet or public-mainnet latency guarantees.

See [machine-readable measurements](submitted-offers/validation.json), [isolated BCHN results](submitted-offers/isolated-atomic-results.json) and [confirmed loopback browser screenshot](submitted-offers/loopback-confirmed.png). Production read-only verification is reproducible with `cd frontend && node scripts/verify-submitted-offers-live.mjs DEPLOYED_SOURCE_SHA`.

Final validation: **168 frontend tests in 32 files**, **8 browser tests**, **2 isolated BCHN integration tests**, root and frontend TypeScript checks, compiled-covenant consistency and the production build passed. A final 27-test UI rerun also verified that the acceptance notice changes to independently verified status when the queue updates; its synthetic warm render measured **113 ms**. Earlier overlapping runs hit memory-pressure timeouts; the completed reruns above passed. No real BCH was spent.
