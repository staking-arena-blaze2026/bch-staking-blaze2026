# Automatic Cashonize restoration repair

Post-baseline BCH Blaze work, 2026-11-16. Parent deployed source: `491452a`.

## Confirmed failure mechanism and limits

The previous owner stopped active wallet handshakes after 2, 6 and 14 seconds, ended restoration at 30 seconds, and left a reachable relay listening passively. Its independent transport loop stopped after four attempts, with only a wallet message resetting the budget. An already-open, silent wallet could therefore remain paired but never receive another request, even while the application stayed visible and online. Manual Retry sent another `updateConnection(..., connected)` on the same manager/client, explaining recovery without a new pairing. These code paths and delayed-success behavior are reproduced in automated tests; no user-specific real Cashonize wire trace was captured.

Installed WizardConnect core/dapp 0.2.5 was inspected directly. `RelayClient.connect()` returns after creating its subscription, `isConnected()` means a subscription exists, and `connection` fires after EOSE **or a 5-second optimistic fallback**. None proves wallet liveness. `DappConnectionManager.updateConnection()` starts an unawaitable asynchronous `dapp_ready` publication; constructor-restored paths are cached identity only. The SDK's Nostr pool bounds connection establishment and individual publications (3 seconds and 4.4 seconds respectively); the adapter additionally bounds subscription readiness at 7 seconds.

The protocol requires a wallet to answer `dapp_ready(wallet_discovered=false)` even if already paired: https://docs.riftenlabs.com/wizardconnect/protocol/. Cashonize's current connection store delegates protocol state to its SDK manager: https://github.com/cashonize/cashonize-wallet/blob/main/src/stores/wizardconnectStore.ts. Browser/wallet/relay timing is not inferred from cached pairing presence.

## Recovery behavior

- One owner, manager and relay survive normal rendering and StrictMode effect replay. A real unmount releases them. Restore always reuses the saved transport credentials and pinned peer; it never starts a new QR pairing.
- Subscription readiness requests the saved-session handshake immediately. Unconfirmed wallet sessions retry after 2, 4, 8 and 16 seconds, then every 30 seconds. The initial 30-second threshold changes the UI to a delayed-recovery status with manual Retry available; it does not stop automatic recovery.
- Transport failures use their own serialized exponential backoff, capped at 30 seconds, without a finite outage budget. A reconnect closes the prior subscription/queue before reopening the same client. Recovery probes explicitly set `wallet_discovered=false` and omit stale protocol selection because the SDK retains discovery state across reconnects. Identical SDK ready publications share one in-flight promise; a reactive protocol-confirming ready is serialized after a pending proactive ready instead of being discarded. Signing requests are never merged or generated by recovery.
- Browser offline suppresses handshakes and connection attempts; online/focus/visibility and relay readiness drive recovery without waiting for a user click. Offline notification immediately revokes wallet liveness. Timers remain capped and cleanup stops both loops permanently.
- Only SDK `walletready` establishes live wallet authorization. Cached paths and optimistic relay readiness never do. Existing path pinning, per-manager storage guards, network validation, worker authorization revisions and transaction approval/input checks remain mandatory. No journal, network key or signing code changes.
- Local Disconnect clears the pairing and cancels retries. A remote disconnect immediately removes financial liveness. The SDK's existing 8-second grace permits a watchdog reconnect; if no new wallet handshake arrives before the SDK emits disconnect, the owner persists invalidation and stops. Protocol mismatch, peer mismatch, corrupt credentials and identity changes also stop restoration. Silence alone is availability failure, never revocation evidence.

Diagnostics contain fixed state labels and elapsed page milliseconds; SDK transport network logging is disabled because it includes peer fingerprints. No credentials, wallet identifiers, URIs, public paths or transaction contents are logged by the recovery instrumentation.

## Verification boundary

`walletRestorationSdk.test.tsx` runs actual RelayClient encryption/decryption, peer authentication, timestamp filtering, subscription readiness, DappConnectionManager, session persistence and StrictMode ownership. Only the external Nostr pool is replaced with an in-memory delivery service. A paired protocol peer starts at 65 seconds, answers an automatic handshake, survives a transport interruption with the same manager, and stays open while the app is unmounted/reopened and restores again. This is a real SDK round trip, **not real Cashonize**.

React regressions additionally exercise connect/close/reopen, initial handshake failure followed by automatic success at 60 seconds, internet loss/return, transport recovery, stale cached paths, identity changes, protocol rejection, explicit disconnect, remote revocation across reopening, pending record preservation, storage denial and late handshake completion. Relay regressions cover serialization, capped long-outage retries, availability recovery, permanent cleanup, saved peer preservation and coalesced publications. Browser tests cover persistent Chromium process restart, navigation and actual IndexedDB pending records with a synthetic wallet.

Real mainnet Cashonize acceptance and live reconnect timings require the owner's existing browser pairing. This execution environment exposes no attached browser or Chrome debugging endpoint for that profile. No profile/credentials are copied, no fresh real wallet is created, and no real transaction is requested or signed. Automated timing uses virtual time and is not a live latency measurement. Deployment and final check results are reported with the source commit in the task response.

## Follow-up: silent subscription and ineffective manual Retry (2026-11-16)

The owner's initial success report was subsequently withdrawn: restoration and manual saved Retry still failed. Production acceptance is therefore **not established** by the earlier report.

A missing recovery path is now reproduced against deployed-source parent `c1db2c2`: a Nostr subscription can report EOSE/readiness while no longer delivering wallet replies. `recover()` returned immediately whenever `reachable` was true, so manual Retry only published another handshake on that same ineffective subscription. The previous test pool always delivered messages after readiness and did not exercise this failure. Both automatic and manual silent-subscription cases fail against the unmodified parent in an isolated worktree with distinct test transport keys.

The relay now starts a wallet-reply watchdog only for requested recovery probes. No authenticated wallet reply within 15 seconds causes a serialized subscription refresh; subsequent unanswered cycles use 30 seconds. A valid wallet reply clears the watchdog and resets that delay. Refresh reuses the same relay client, credentials, peer and SDK manager, clears the previous subscription/queue through SDK disconnect, and retains the SDK replay cutoff. Explicit disconnect/cleanup cancels the watchdog. Manual saved Retry requests a refresh even when EOSE claimed readiness; online/focus events remain passive hints. Repeated refresh notifications are coalesced with the existing connection guard and a two-second minimum interval. No signing, chain-validation or journal behavior changes.

Privacy-safe diagnostics now distinguish requesting a handshake from successful publication, and report when an unanswered wallet probe triggers a subscription refresh. Errors, identifiers and message contents are not logged.

The expanded real-SDK encrypted round-trip tests cover a silently lost initial subscription and a second silent loss immediately before manual Retry. Unit regressions verify 15/30-second refresh timing, stopping on wallet replies, manual refresh while nominally connected, click coalescing and permanent cleanup. A separate read-only public relay probe with synthetic peers exchanged four encrypted ready handshakes successfully; it establishes public relay reachability at that time, **not** Cashonize acceptance or the owner's particular failure cause. Live Cashonize confirmation remains required.

Follow-up validation: full frontend suite **172/172 tests in 32 files** (117.25 seconds); focused relay/encrypted SDK regressions **14/14**; frontend TypeScript and `npm run blaze:build` passed. Neither automated success nor synthetic public-relay round trips substitutes for a repeated real Cashonize close/reopen check.
