# Fast public marketplace index (BCH Blaze, post-baseline)

## Measured problem

Read-only live profiling on 2026-11-15 (`discovery-profile.json`): two legacy marker histories each contained **12,596** entries. Fetching them with provider session/chain-identity setup took **3,635 ms + 2,707 ms**, transferring approximately **2.4 MB** of history JSON across both providers. A known announcement fetch/parse with a new connection took **1,696 ms**. Independent genesis validation and full current state replay on both mainnet providers took **23,864 ms**; 74 individual header calls across the complete profile consumed 14.24 seconds. Parsing the 90-byte announcement is local; transport round trips, sequential MTP reads, fresh sessions and repeated history downloads dominate.

The old browser repeated full histories on every page/refresh, then sequentially opened sessions for up to 20 transaction candidates. A fresh production Chromium incognito context displayed no `c14b3170fd156ee0` card within **61.71 seconds** (`marketplace-before.json`). This was a real timeout observation, not a throughput estimate.

Local Chrome initially still took **3.52 seconds cold / 1.11 seconds reload** despite a 13 ms index fetch: the full application and wallet SDK were delaying the initial list. A dependency-free startup renderer now fetches the same bounded index before those modules initialize, renders only unverified candidate hints, and hands the same response to React without a second download. React removes the startup view when its catalog is ready. This reduced the local measurement to **0.716 seconds cold / 0.432 seconds reload**, while independent financial-state verification remained about 21 seconds. Both measurements used official Chrome for Testing 157.0.8103.78, no wallet, fresh incognito storage, and real public mainnet providers. See `marketplace-local.json` and `marketplace-local-fast-start.json`.

## Architecture and automatic operation

GitHub Pages serves `public-index/{mainnet,chipnet}/index.json`. The versioned schema includes the first **20** candidate hints, revision hash, observation time, coverage/catch-up information and references to additional content-addressed pages of 20 hints. Each additional page is SHA256 checked against its filename. No visitor downloads the scanner checkpoint or scans discovery marker histories. Existing historical configurations remain migration hints. The mainnet configuration was extracted from the actual transaction and independently verified, rather than invented or copied from another checkout.

`scripts/update-public-index.ts` runs a read-only Electrum scanner on **every** website workflow execution, even when the source SHA is unchanged. It reads both dedicated and legacy histories on all configured providers; session chain-identity checks keep networks separate. It persists successful negative results keyed by immutable transaction ID and retries failed reads. This avoids re-downloading unrelated raw transactions after restart. Unknown announcements are processed in bounded batches (default 1,500 transactions per network/run; maximum 5,000). There are at most four raw retrievals per independently pinned provider session. Parent announcements are retried fairly, including child discovery, confirmation, disappearance and reorganization observations. Direct announcement heights/statuses are refreshed from live history each run. All-provider outages retain previous candidates and timestamps; incomplete provider coverage cannot evict candidates. A disappearance changes the hint status, never deletes recovery records.

The workflow restores the last checkpoint from the **Blaze website fork**, updates both networks, builds, records the source commit and publishes compiled output plus public index/checkpoint. All current hints survive a scanner failure because the prior Pages deployment remains live. Old and current pagination generations are retained; resources older than those generations may need an explicit refresh. No separate paid service or creator-submitted JSON is required. A creator still announces in the existing creation/preparation transaction, and needs no further transaction or wallet approval for indexing.

Reviewed copies of the website automation are in `deploy/blaze/`; their actual deployment location is `.github/` in `staking-arena-blaze2026/staking-arena-blaze-site`. Only that fork is an allowed publisher. Manual recovery: `gh workflow run deploy.yml --repo staking-arena-blaze2026/staking-arena-blaze-site`. Scanner recovery can also be run locally with `npx tsx scripts/update-public-index.ts`; use public generated state only.

GitHub schedules are best effort, have a five-minute minimum, can be delayed/dropped under load, run only from the default branch, and are disabled on inactive public repositories after 60 days. They do **not** promise five-minute appearance or mempool coverage. Durable full-history comparison on every successful run catches confirmed announcements missed during downtime, regardless of how many blocks elapsed; negative checkpoints prevent repeating raw downloads. A 0-conf announcement that disappears entirely between scheduled observations cannot be guaranteed captured. Pending hints that were observed remain retained after eviction. Operators must monitor workflow failures and inactivity and can dispatch recovery; this design provides eventual confirmed catch-up, not an always-on mempool subscription. See https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule .

## Marker compatibility

New markers are P2SH of `PUSH UTF8("StakingArena/BLAZE/discovery/v2/" + network) OP_DROP OP_TRUE`. Mainnet, chipnet and regtest have distinct scripts/scripthashes. Redeem scripts are public, deterministic and anyone spendable. The output stays 23 bytes and **1,000 satoshis**; fees stay **10,000 satoshis**. The existing 90-byte payload, covenant parameters and one-approval direct/chained creation path remain intact. Genesis and saved-plan validation recognize both the original OP_TRUE P2SH and the current network's marker. Existing immutable covenant artifacts are unchanged. The real mainnet genesis `c14b3170fd156ee0b5cdefba0241981407a481caa08d7169b2e07ea5caccb2e5` stays in the migration catalog and legacy index. Scanning continues for legacy announcements, including old clients.

## Discovery does not establish financial state

The startup renderer and full frontend whitelist immutable configuration fields, bounds responses to 256 KiB and pages to 20, rejects malformed paths/network/schema/fields and conflicting duplicate hints, and never accepts a snapshot from the index. Index status means **observed**, not blockchain verified. 0-conf candidate hints are visibly provisional. Previously seen but missing announcements are labeled retained/unobserved. Candidate cards render immediately without Cashonize or browser identity. Optional retained first-page hints and display snapshots use network-specific cache keys; restored snapshots always start stale/unverified.

Two dedicated background workers verify only the displayed 20-entry page, using separate provider transports. Obsolete page/network reads terminate their workers; timeout/failure resets a read worker. Identical concurrent read requests are coalesced. Confirmed display snapshots refresh at most every two minutes, provisional snapshots every 15 seconds; failed reads retry on the next visible polling interval. The index refreshes every 60 seconds and times out after eight seconds, with explicit retry. Verification times out after 60 seconds. No history-based shortcut is used to skip consensus, mempool or allocation checks.

Only txid-validated immutable raw bytes are retained in a peer-scoped, 512-entry/byte-bounded memory cache. History, proofs, live outputs, tips and provider agreement are reread. MTP headers are fetched concurrently and still linked/checked in order. Reorganization handling, 0-conf ancestry, input/CashToken checks and conflict persistence remain in the existing verification path. Read workers reload conflict evidence; financial operations also reload it. A cached or indexed hint never authorizes a wallet request. Existing financial action code independently refreshes/revalidates before explicit wallet authorization and again through the wallet transaction path. Chipnet's consensus conflict remains a transaction block; no chipnet configurations, journals or investigation records are removed.

## Validation and limits

Results and exact deployed revisions are recorded below after the production acceptance run. No real transaction is created, signed or broadcast. Local isolated regtest signatures and broadcasts are test-only. The initial baseline used isolated Playwright Chromium. Production acceptance uses official Google Chrome for Testing with a fresh incognito context, no seeded storage and no wallet; its exact version is recorded in the acceptance JSON.

The historical marker API still downloads full histories **once per scheduled scan**, because public Electrum provides no paginated historical cursor. This load is centralized and bounded by existing provider budgets; it is removed from visitors. Very large future marker histories can exceed provider budgets and require a proper persistent Electrum subscription service or block indexer. Scheduled Actions cannot guarantee immediate observation of short-lived mempool events. Browser resource use is bounded per page; loading more pages accumulates configuration hints for the current session, up to the manifest's bounded page count. Full blockchain replay still costs network time; unverified/stale states remain explicit and do not enable transactions.

## Completed local checks

- Root and frontend TypeScript checks and the public production build passed; immutable compiled covenant artifacts are preserved.
- **146 frontend unit tests in 29 files passed** (15-second per-test timeout on this small VM). This includes fresh discovery without a wallet, bounded two-worker verification, stale-state action refresh before wallet calls, malformed index entries, startup HTML safety, and one-download handoff from startup rendering to React.
- **25 Electrum/index/provider unit tests passed**: exact token decoding, proof failure, reorg rollback, provider failover/conflict, 5,000 irrelevant entries, durable restart, outage/recovery, automatic new hints, 0-conf/confirmation/eviction, cross-network rejection and conflicting/malicious hints.
- **Seven real Chromium browser scenarios passed**: independent worker verification over loopback WSS; provider failure/reorg; signed test-journal recovery across reload; navigation/layout; two fresh independent profiles discovering V3/V4 from the automated updater; 1,000-candidate bounded pagination; simultaneous visitors without wallet identity. The browser checks observed no discovery-marker history reads or browser financial broadcasts. Synthetic transactions remain in isolated fixtures.
- The isolated **BCHN 29.2.0** run passed atomic offers (all asset pairings and recovery), chained genesis, automatic V3/V4 discovery and index ingestion at 0-conf/confirmation, and all six tip-change/conflict/funding tests. The interrupted final zero-conf suite was rerun separately and passed all its BCH/token pairings and dependent offer/claim flows. These are ten test cases across five relevant suites, not a claim that every historical root integration suite was rerun. No original service, wallet or chain state was used.

Detailed after-profile (`discovery-profile-after.json`): payload parsing averaged **0.053 ms** over 1,000 parses. Per provider, clock verification took **520–666 ms**, genesis retrieval/validation **1,264–1,301 ms**, and remaining state/proof/output replay **5,130–6,093 ms**. Full independent verification including both connection/identity sessions took **18.30 seconds**. The legacy history downloads still took **7.03 seconds** in that operator-only profile; visitors make neither call. Timing conditions differ across measurements; these are observed samples, not percentile guarantees.

Automatic ingestion of newly created V3/V4 vaults was verified against isolated BCHN and the same updater used by deployment, without manually inserting their configurations. No new real mainnet/chipnet vault was created for this task, as requested. Production acceptance below measures discovery and verification of the existing real mainnet vault; it cannot attest to an unperformed real-wallet creation.
